# GitLabへの移行

対象は、リポジトリ管理、Web公開CI、GitLab Pagesへの公開です。iOS / Androidのソースも同じリポジトリで管理します。ネイティブアプリのストア配信は別の手続きとして扱います。

## 準備済みの構成

- `.gitlab-ci.yml`の`deploy-pages`がデフォルトブランチだけを公開します。
- Node.js 22で`node scripts/sync-web.mjs`を実行し、生成した`web/`を`pages.publish`で公開します。
- 公開前に必須ファイルの存在・サイズ、manifestのJSON、HTML内のJavaScript・import map、Service Workerと広告設定の構文を検証します。
- Web公開はNode.js標準機能のみで動作します。`npm ci`、Capacitor、Xcode、Android SDKは不要です。
- `web/`と`output/`は生成物としてGit管理から除外します。元の画像やネイティブソースは別途Gitで管理し、ローカルの生成物は削除しません。

CI構文はGitLab 17.10以降を対象としています。`pages.publish`のディレクトリはPagesのartifactに自動で追加されます。[GitLab CI公式資料](https://docs.gitlab.com/ci/yaml/#pagespublish)

移行先のURLは、作成したプロジェクトの **Deploy > Pages** で確認します。新規プロジェクトではunique domainが既定で有効なため、アカウント名・プロジェクト名から公開URLを推測しません。[GitLab Pages公式資料](https://docs.gitlab.com/user/project/pages/#unique-domains)

## 公開前のお知らせとセーブ移行

先に、現在公開中のゲームのお知らせ欄で移行予定とバックアップ手順を案内します。新サイトの起動・復元を確認するまで、旧サイトとその「セーブデータ」機能を利用可能にします。旧サイトから新サイトへの自動転送は、バックアップの機会を奪うため、この段階では設定しません。

セーブはWeb版のlocalStorageに保存されます。別のドメインでは新しい保存領域になるため、バックアップせずに新サイトへ移ると、それまでの進行状況を引き継げません。移行処理が旧サイトのセーブを削除するわけではありません。旧サイトの公開終了、ブラウザのデータ削除、端末の紛失等で旧データにアクセスできなくなると、バックアップなしでは復元できません。[localStorageの仕様](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

プレイヤー向けの手順は次のとおりです。

1. 旧サイトで「セーブデータ」を開く。
2. パスフレーズを設定し、暗号化バックアップの`.fwsave`ファイルを書き出す。
3. ファイルとパスフレーズを保管する。パスフレーズの再発行はできない。
4. 新サイトで「セーブデータ」を開き、ファイルと同じパスフレーズで復元する。
5. 恒常進行・メイン出撃・並行タワー出撃が復元されたことを確認する。

詳細は[端末内セーブと暗号化バックアップ](LOCAL_SAVE.md)を参照してください。PWAは新しいURLで開き、必要に応じてホーム画面へ再登録します。旧PWAのショートカットだけでは新URLへ切り替わりません。

iOS / Androidアプリの端末内保存はWeb公開ドメインとは別です。公開URLだけの変更でネイティブアプリのセーブを削除する処理はありません。アプリを削除・再インストールする前は、同様にバックアップを保管してください。

## コード・履歴の移送

1. 認証済みGitLabアカウントの管理可能なnamespaceに空のプロジェクトを作成する。既存のプロジェクトを上書きしない。
2. 作業中の変更を確認し、既存のAndroidアイコン変更と未追跡の`ios/`ソースを含む必要なファイルをGit管理へ取り込む。未追跡の仕様書は内容を確認して扱いを決める。`output/`配下のIPA・archive・DerivedData・シミュレータ生成物、秘密鍵、ローカル設定を含めない。
3. 移行先へGitの履歴・必要なブランチ・タグを移送する。履歴を書き直さず、移送前後のcommit SHAとタグを照合する。
4. 移行先のデフォルトブランチ、Pages公開範囲、Runnerが利用可能なことを確認する。
5. GitLabのCI Lintと実際のpipelineを確認し、Pagesの初回公開を確認する。
6. 確認後に普段のpush先をGitLabへ変更する。旧GitHubのURLと履歴は切り替え・復元のために記録しておく。

GitHubのIssue・PR・Release等を移す必要がある場合は、Gitのpushとは別に移送します。Gitだけではこれらの管理情報やCI変数は引き継がれません。

GitHub Pagesのワークフローは、お知らせを旧サイトへ配信する間は残します。旧サイトを終了する段階で、GitHub側の公開設定とワークフローを停止します。

## 公開URLと広告・ストア情報の変更

新しい公開先が確認できてから次の値を更新します。公開中のURLを未確認の候補URLに置き換えません。

| 対象 | 変更・確認内容 |
| --- | --- |
| `index.html` | canonical、`og:url`、OGP・Twitter画像の絶対URL |
| `README.md` | Web版の公開URL、GitLabリポジトリへの案内 |
| `docs/PLAY_CONSOLE_DRAFT.md`、`docs/GOOGLE_PLAY_RELEASE.md` | プライバシーポリシーURL |
| `privacy-policy.html` | 案内内容とリンクが新しい公開先で正しいこと |
| `manifest.webmanifest`、`sw.js` | 相対パスが新しい公開先で動作すること。アプリ更新時にキャッシュ名も更新する |
| App Store Connect、Google Play Console | 開発者サイト・サポート・プライバシーポリシーURL |
| AdMob、AdSense | 開発者サイトURL、新しいサイトの登録・審査・公開状態 |

`app-ads.txt`はストアに登録した開発者Webサイトのドメイン直下でアクセスできることを確認します。プロジェクト名を含むパス配下に置くだけでは不十分です。`ads.txt`も実際の公開ドメインで確認します。[AdMob公式資料](https://support.google.com/admob/answer/9363762?hl=ja)

現在の`fireworks.config.js`には広告IDが設定されています。CIには広告変数の既定値を追加していないため、通常はこのファイルをそのままコピーします。`scripts/sync-web.mjs`は、広告関連の環境変数を一部だけ指定すると、未指定の広告IDを`null`に置き換えます。GitLabのCI変数で広告設定を上書きする場合は、必要なAndroid・iOS・AdSenseのIDと広告オプションを一式設定し、生成された設定を確認してください。

## 切り替え時の検証

- 新しいHTTPS URLでゲームが起動し、地図・GPSの許可と表示が動作する。
- 旧サイトでバックアップを書き出せる。新サイトで復元し、主要な進行値と出撃状態が一致する。
- お知らせをタイトル画面とゲーム中から開ける。既読状態・未読表示・バックアップへの導線が動作する。
- 再読み込み後もセーブが残る。PWA登録、Service Worker更新、オフライン起動を確認する。
- manifest、アイコン、プライバシーポリシー、広告設定、`app-ads.txt`、`ads.txt`が正しいURLで取得できる。
- URLとストア掲載情報が新しい公開先を指している。広告の登録・審査が必要な場合はその状態を記録する。
- ネイティブソースがGitLabで管理されている。iOS / Androidの配信が必要な場合は別途ビルド・実機検証を行う。

問題が見つかった場合は旧サイトでバックアップできる状態を保ち、修正と再検証が終わるまで旧公開を終了しません。

## 検証記録（2026-10-12）

- CIのYAML解析と公開スクリプトのローカル実行、必須10ファイル、JSON・JavaScript構文の検証に成功。
- Chromeでスマホ縦画面・横画面のお知らせ表示、一覧・詳細・未読フィルター、既読の再読み込み後の保持、背景クリック・Escape・フォーカス復帰を確認。
- タイトルと探索画面からのお知らせ閲覧で、ゲームの保存領域が変化しないことを確認。
- お知らせからセーブ画面へ移動し、暗号化バックアップを書き出し、異なるローカルオリジンで資源・通貨を復元するテストに成功。
- ネイティブ実行を模擬した環境でWeb向けのタイトル告知を非表示にし、不正な既読記録からもお知らせを開けることを確認。
- GitLab上のCI Lint・pipeline・Pages公開、現行公開サイトへの告知配信、実機でのGPS・広告・PWA再登録は、認証と公開先の確定後に実施する。
